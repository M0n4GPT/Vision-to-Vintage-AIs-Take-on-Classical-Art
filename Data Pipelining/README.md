# Data Pipelining
**Unit 8 Requirements: Machine Learning System on Chameleon**

This section outlines how our project meets the key Unit 8 requirements for a machine learning system deployed on the Chameleon cloud. We address data sourcing, persistent storage, offline and online data handling, an ETL pipeline, and an interactive dashboard to satisfy the unit's guidelines. 

**Data Source: Kaggle Art Datasets **

We leverage public art datasets from Kaggle as our primary data source. In particular, the WikiArt dataset (over 120,000 images spanning 3,000+ artists and 200+ styles (WikiArt - Learn about the artist from the artwork - Kaggle)) and the Best Artworks of All Time dataset (artworks of the 50 most influential artists, with accompanying Wikipedia metadata (Best Artworks of All Time - Kaggle)) provide a rich collection of images. These datasets supply a diverse range of paintings and artwork images for model training and evaluation. We will obtain the data using the Kaggle API/CLI, which allows programmatic download of datasets using simple commands (e.g. kaggle datasets download <username>/<dataset-name> --unzip) (kaggle-api/docs/README.md at main · Kaggle/kaggle-api · GitHub). By using Kaggle's reliable data sources, we ensure our model is trained on a varied and reputable corpus of artwork imagery, satisfying the requirement for a robust data source. 

**Persistent Storage on Chameleon **

All large data and artifacts will be stored on a Chameleon persistent volume attached to our instance. This dedicated storage (backed by Chameleon's OpenStack-based infrastructure) will hold everything that is not tracked in Git, including the downloaded datasets, preprocessed images, trained model files, and container images or checkpoints. Using a persistent volume means that our data remains intact across experiment runs or instance restarts – we can detach the volume and reattach it to new Chameleon instances without data loss (Data Storage, Management, and Sharing on Chameleon | Chameleon). This approach is analogous to using a cloud block storage or shared file system, as Chameleon’s persistent storage behaves like a mounted drive that multiple instances (or users) can access if permitted (Data Storage, Management, and Sharing on Chameleon | Chameleon). By utilizing Chameleon’s persistent storage, we fulfill the requirement to keep training/test artifacts and data available long-term, rather than relying on ephemeral instance storage. 

**Offline Data Management and Preprocessing **

Our offline data consists of the unstructured image files from the Kaggle art datasets, which we will manage in a structured way on the persistent volume. We plan to implement a data lakehouse-style repository for these images: the raw data will be stored initially, then processed into cleaned, ready-to-use formats with an accompanying metadata layer for cataloging (8-data-sp25.pdf) (8-data-sp25.pdf). All images will be saved in an organized directory structure (for example, grouped by artist or art style), and we will generate metadata tags for each image such as artist name, style/genre, image dimensions, and file format. This metadata will be stored in a queryable form (e.g. a CSV or lightweight database index) to enable easy searching and filtering of the dataset. As we ingest the images, we also plan to extract any available embedded metadata (many images include EXIF or descriptive data) using libraries like Pillow, and record statistics like image size or aspect ratio for each file (Enable Computer Vision on a Lakehouse | Databricks Blog). Storing these details alongside the files (in a “data catalog”) is aligned with best practices for large image collections – metadata and image stats are captured as data lands in storage to facilitate later analysis (Enable Computer Vision on a Lakehouse | Databricks Blog). In summary, our offline data storage will act as a data lakehouse: unstructured images on disk with a management layer of metadata on top, ensuring the data is both persistently stored and easily discoverable. 

**ETL Pipeline Implementation **

We implement an Extract-Transform-Load (ETL) pipeline to automate moving data from Kaggle into our Chameleon environment and preparing it for use. This pipeline addresses data extraction, preprocessing, and loading in a repeatable way (What are Data pipelines? - Kaggle): 

**Extract:** The pipeline connects to Kaggle via its API to download the art datasets. We will use the Kaggle CLI in a script or an Airflow task to fetch the latest dataset files (for example, using kaggle datasets download commands (kaggle-api/docs/README.md at main · Kaggle/kaggle-api · GitHub) with the appropriate dataset identifiers). This step pulls the raw images (and any accompanying metadata files) from Kaggle and stores them on the Chameleon persistent volume. (If direct API access is not possible, we will perform a manual download and then integrate the files into the pipeline, but the process is the same from this point onward.) 

**Transform:** Once the raw data is extracted, the pipeline performs cleaning and transformation. This includes unzipping or organizing the image files, removing any corrupted or duplicate images, and converting all data into a consistent format usable by our model (e.g. ensuring image file types and dimensions meet our model requirements). We also merge data from the two sources (WikiArt and Best Artworks) into a unified structure and apply the metadata tagging scheme. For example, if the two datasets have different directory layouts or label formats, this step will map them to a common format (such as a unified CSV of image paths with labels like artist/style). Any needed feature engineering or dataset splitting (train/validation/test split generation) is also done here. The transformation step results in a clean, standardized dataset ready for model training and stored in our persistent storage (in the structured directories plus metadata files as described above). 

**Load:** In the final stage, the processed data is “loaded” into our system’s data lakehouse repository. In practice, since we are working on a single environment, this means the transformed files are already on the persistent volume. Here, loading is more about updating indices or databases that keep track of the dataset. For instance, we might update a dataset catalog file or a database table with the new images and their metadata. This ensures the latest data is registered and accessible to the model training pipeline. After this stage, the data is fully prepared and persisted, and we can trigger model training or other analysis on it. 

We plan to automate this ETL workflow using Apache Airflow or a similar orchestration tool. With Airflow, we can define the above steps as tasks in a Directed Acyclic Graph (DAG) – for example, an Airflow DAG could first run the Kaggle download, then run a Python task for preprocessing, then a task to update the data registry (Airflow DAG Kaggle Data to Looker Studio ETL | by Pravish K | Medium). This automation not only saves time but also ensures consistency (the same process can be rerun to update the dataset or reproduce the environment if needed). It’s also flexible in scheduling: Airflow (or cron jobs) can trigger the ETL pipeline on a schedule or on demand. In essence, the pipeline acts as the “glue” coordinating data operations, which is a core concept of production ML systems (8-data-sp25.pdf). By having a solid ETL pipeline, we fulfill the requirement for systematically handling the offline batch data ingestion and preparation. 

**Simulated Online Data Ingestion**

In addition to the large offline dataset, we will simulate an online data stream to mimic real-time user inputs. This addresses the requirement of handling streaming or real-time data alongside batch data. The scenario is that museum visitors upload images through the Met exhibit interface – since we cannot have actual users during development, we simulate this by periodically injecting new images into our system. We will implement a small script or service that acts as a data producer, which could be scheduled (e.g., via Airflow or a simple loop with sleep) to run at regular intervals. This script will pick an image (for example, from a folder of new artwork images not in the training set, or generated on the fly) and then feed it into our pipeline as if a user just uploaded it. In a real-world deployment, such streaming ingestion might use a message broker (with producers and consumers) to handle multiple sources and ensure reliability (8-data-sp25.pdf) (8-data-sp25.pdf). For our simulation, a simpler approach suffices: the script can call a function or send an HTTP request (webhook) to our running system, delivering the new image. 

Once the image is received by the pipeline (the consumer side), we process it through the same transformation steps as the offline data (e.g., apply any preprocessing needed) and then run it through the trained model for inference. The result could be logged or stored, simulating how the system would respond to a live user submission. We will time-stamp and log these incoming images to gather metrics on how many images are processed and how the model performs on them. This continuous trickle of new data serves two purposes: it tests our deployment’s ability to handle incremental data, and it provides a form of ongoing evaluation (we can see if model accuracy holds up on new, potentially unseen artworks). By mimicking a streaming data pipeline in this way, we satisfy the online/real-time data requirement without needing a full production infrastructure. It ensures our system isn’t just a static batch process but can adapt to new inputs dynamically. 

**Interactive Dashboard for Monitoring**

As a stretch goal (and to earn the difficulty point), we plan to build an interactive dashboard to monitor the system’s data and performance metrics. This dashboard will give us and stakeholders a live view of important indicators, addressing the requirement for visibility into dataset growth and model performance over time. We are considering using either Plotly Dash or Streamlit for this component. Both are powerful Python frameworks for creating data apps: Plotly Dash allows building rich interactive web interfaces purely in Python (it’s built on Flask/React and requires no manual HTML/CSS, making it straightforward to go from data to dashboard) (Create Interactive Dashboard Using Python Dash | by Nur Yaumi | Medium), while Streamlit offers a very quick way to build and share data applications with minimal code, ideal for rapidly prototyping such a tool (Monitor Your Model Performance with Python Streamlit | by Chris Kuo/Dr. Dataman | Dataman in AI | Medium). 

The dashboard will include visualizations and statistics such as: 

Dataset Size & Composition: We will display the number of images in the dataset, broken down by category (e.g., how many per art style or per artist). This can be a simple counter and a bar chart or pie chart, updated whenever the offline data is refreshed or new images are added via the simulation. 

Model Performance Over Time: Here we will track metrics like model accuracy, loss, or other evaluation scores across training iterations or different model versions. For example, if we retrain or fine-tune the model periodically, the dashboard might show a line chart of validation accuracy over each training run (so we can see improvements or detect degradation). We can also include the latest evaluation on the simulated online images to monitor if the model’s performance on “fresh” data is holding steady (important for detecting model drift). 

User Interaction Metrics: Although our “users” are simulated, we will monitor how many new images have been ingested and processed. The dashboard might show the count of images uploaded through the Met exhibit interface simulation per day, or a timeline graph of when images were received. We can also track the inference latency for those images (how quickly the model processed them), which is an operational metric that matters for user experience. 

The dashboard will be deployed on the Chameleon instance (for example, running Dash on a Flask server or using Streamlit’s web interface). This allows us to access it via a web browser to observe the system in real time. By implementing this dashboard, we demonstrate an ability to monitor the ML system in production-like settings, covering metrics for both data and model performance. This fulfills the dashboard requirement and provides transparency into the system’s operation, which is crucial for ongoing maintenance and improvement. 

Overall, through the components above, our project comprehensively addresses the Unit 8 requirements: we have a reliable data source, proper persistent data storage, organized handling of offline (batch) data, a clear ETL pipeline, simulation of online (streaming) data ingestion, and a plan for an interactive monitoring dashboard. Each of these elements is designed to work cohesively on Chameleon, leveraging its capabilities to host a full-fledged machine learning system. The approach ensures that our ML workflow is reproducible, scalable, and observable, aligning with best practices highlighted in the course.
